# DRLQN vs Duck Harness: submission-oriented comparison

## Executive finding

The current DRLQN is architecturally sophisticated but submission-limited by its interface and training regime. It trains the CPU-sized DRLQN-XS online from scratch on first contact, represents clicks only through 24 connected-object slots with five local offsets, and explores by expanding a deterministic state graph. The Duck Harness instead supplies a large pretrained model with structured segmentation, full action/history context, arbitrary mouse coordinates, ephemeral Python search, batched actions, repeated passes, and extensive runtime instrumentation.

The largest expected gain is therefore not a larger differential residual network. It is to make DRLQN's action proposals and training data closer to Duck's effective interface while retaining DRLQN as a cheap policy/value student.

## Important differences

| Area | DRLQN | Duck Harness | Consequence |
| --- | --- | --- | --- |
| Prior knowledge | Online RL from random initialization | Large pretrained reasoning model | DRLQN spends scarce game actions learning basic mechanics |
| Perception | Same-color 4-connected objects plus compact shape features | Segmentation with shape hashes, containment, adjacency, frame history, image context | DRLQN loses logical cells merged into one component and weakly represents relations/history |
| Mouse actions | Object centroid plus four object-sized offsets | Any `(row, col)` generated by code | DRLQN cannot express many empty-cell, lattice, bridge, paint, mirror, or path-extension actions |
| Planning | BFS only over already observed deterministic transitions | Writes BFS/DFS/beam/custom search after inferring mechanics | DRLQN cannot search a compact learned symbolic simulator before paying environment actions |
| Memory | Four scalar trace features | Full transition history and persistent transcript context | Hidden-state and rule-switching games are difficult for DRLQN |
| Evaluation | Five synthetic games, one main run | Official game set, many passes, competition simulator, artifacts and significance checks | Local RHAE does not establish submission readiness |

## Implemented modification

The branch `codex/hybrid-spatial-distillation` adds an opt-in `HybridDRLQNSolver` and a state-conditioned spatial proposal generator. The fixed 128-action Q head is retained, but the 24 click anchors can now include:

- connected-object centres and adjacent locations;
- inferred logical tile centres on rendered 64x64 boards;
- centres of recently changed regions;
- a coarse fallback lattice for arbitrary-coordinate reachability.

This is deliberately a small compatibility-preserving intervention. Existing object-only tests and checkpoints keep the same action tensor geometry, while the hybrid solver broadens the representable ACTION6 set.

## Recommended next modifications, in priority order

1. **Duck-trace SFT / policy distillation.** Export Duck traces as `(state, valid actions, chosen action/coordinate, outcome)` records. Map each teacher coordinate to the nearest generated spatial proposal and train the Q-router with cross-entropy or large-margin behavior cloning before online RL. Distill value targets from pass-level score and remaining actions.

2. **History encoder.** Replace the four-scalar trace summary with a short transition-token memory: action id, changed-region descriptor, reward/level transition, and object-hash matches across the last 8–32 steps. A small recurrent or causal block is enough; full language reasoning is unnecessary.

3. **Proposal-conditioned coordinate refinement.** Predict a bounded `(dx, dy)` residual around the selected anchor, or add hierarchical coarse-to-fine coordinate heads. This removes the remaining quantization error without expanding Q to 4096 mouse actions.

4. **Mechanic-conditioned planners.** Add deterministic specialists for navigation, Sokoban, Lights Out/linear toggles, matching/memory, and click-sequence games. Use DRLQN as a router over specialists and primitive actions. This is likely more valuable than deeper residual executors.

5. **Offline pretraining before test-time RL.** Generate trajectories from environment packages and scripted/oracle solvers, then train representation, dynamics, action-change prediction, and Q/value heads offline. Online updates should adapt a competent prior rather than create one.

6. **Multi-pass portfolio.** Run diverse seeds/policies per game, including conservative planner-first, exploratory DRLQN, and distilled policy variants. Select or aggregate using internal progress signals and pass-level validation, mirroring Duck's repeated-pass advantage.

7. **Simplify differential runtime until policy quality improves.** The JVP shadow and sparse executor are useful efficiency mechanisms, but they do not address the current dominant errors. Keep them optional and benchmark exact recomputation against a simpler encoder/Q model. Redirect complexity budget to data, action coverage, memory, and planning.

## Submission checks

`scripts/audit_environment_files.py` statically scans an `environment_files` tree for action requirements outside ACTION1–ACTION6/RESET and reports click-heavy environments. It should be run against the mounted competition environment directory before packaging.

The included tests cover rendered tile-scale inference, merged logical-cell click coverage, changed-region proposals, and a hybrid-solver smoke path. GitHub Actions runs the full repository test suite on the branch.
